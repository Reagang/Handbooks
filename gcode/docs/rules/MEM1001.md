# MEM1001: Event handler never detached

| Property | Value  |
|----------|--------|
| Category | Memory |
| Severity | Warning |

## Cause

A class that implements `IDisposable` subscribes to an event
(`publisher.Event += Handler;`) but never unsubscribes
(`publisher.Event -= Handler;`) anywhere in the class.

## Rule description

An event subscription is a reference from the publisher back to the
subscriber. As long as that subscription lives, the publisher keeps the
subscriber - and anything the subscriber's handler captures - alive, even
if every other reference to the subscriber has gone out of scope. For a
long-lived publisher (a static event, a singleton service, a UI element
that outlives the view) this is a classic memory leak. Detaching in
`Dispose()` breaks that reference deterministically.

## How to fix violations

Unsubscribe the handler, typically in `Dispose()`:

```csharp
publisher.Event -= Handler;
```

If the publisher is itself short-lived and disposed alongside the
subscriber, this may be a non-issue in practice - but making the detach
explicit still documents that the lifetime was considered.

## Example

```csharp
// Violation
class Subscriber : IDisposable
{
    public Subscriber(Publisher publisher) => publisher.Changed += OnChanged;
    private void OnChanged(object? sender, EventArgs e) { }
    public void Dispose() { }
}
```

```csharp
// Fixed
class Subscriber : IDisposable
{
    private readonly Publisher _publisher;
    public Subscriber(Publisher publisher)
    {
        _publisher = publisher;
        _publisher.Changed += OnChanged;
    }
    private void OnChanged(object? sender, EventArgs e) { }
    public void Dispose() => _publisher.Changed -= OnChanged;
}
```

## When to suppress

Suppress when the publisher and subscriber are guaranteed to have the same
lifetime and are collected together (e.g. both are fields created and
discarded together with no external references to the publisher), or when
using a weak-event pattern that intentionally doesn't need a manual detach.
