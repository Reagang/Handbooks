# DI1003: Circular constructor dependency

| Property | Value               |
|----------|---------------------|
| Category | DependencyInjection |
| Severity | Warning             |

## Cause

Two or more classes depend on each other through their constructors,
directly or through intermediates - `A` depends on `B`, and `B` (perhaps
through `C`) depends back on `A`.

## Rule description

None of the types in a constructor-injection cycle can be constructed
without the others already existing, so the container can't resolve any of
them without help (property/method injection, a factory, or lazy
resolution). A cycle like this is usually a sign that two components should
be merged, or that the coupling should be broken with an interface,
mediator, or event.

**Detection is best-effort.** This analyzer only follows a dependency
through an interface parameter when exactly one class in the compilation
implements it (an ambiguous interface is skipped rather than guessed at),
and it only looks at each class's constructor with the most parameters.
Cycles that only exist through property injection, service location, or an
interface with multiple implementations won't be caught.

## How to fix violations

- Introduce an interface (or split responsibilities further) so the
  dependency runs one way.
- Use a mediator/event to decouple the two sides.
- If the cycle is intentional (rare), break it with property injection or
  `Lazy<T>` and document why.

## Example

```csharp
// Violation
class ServiceA { public ServiceA(ServiceB b) { } }
class ServiceB { public ServiceB(ServiceA a) { } }
```

```csharp
// Fixed: ServiceB no longer depends on ServiceA
class ServiceA { public ServiceA(ServiceB b) { } }
class ServiceB { }
```

## When to suppress

Suppress if the cycle is broken at runtime in a way this analyzer can't
see (e.g. one side is resolved lazily via `Lazy<T>` or `Func<T>`, or via
property injection instead of the constructor).
