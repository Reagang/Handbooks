# CC1004: Blocking call on async code

| Property | Value  |
|----------|--------|
| Category | Async  |
| Severity | Warning |

## Cause

Code blocks a thread on a `Task`/`ValueTask` via `.Result`, `.Wait()`, or
`.GetAwaiter().GetResult()`, or calls `Thread.Sleep` inside an `async`
method.

## Rule description

Also covers the same pattern documented under `ORG1002` in the
organization philosophy pack.

Blocking on async code (sync-over-async) occupies a thread pool thread for
the duration of the operation instead of releasing it, which reduces
throughput under load and can deadlock when a `SynchronizationContext` is
present (classic ASP.NET, WPF, WinForms). `Thread.Sleep` inside an `async`
method has the same effect: it blocks the thread instead of yielding it via
`await Task.Delay(...)`.

## How to fix violations

- Await the task instead of blocking on it, and let `async` propagate up
  the call stack.
- Replace `Thread.Sleep` with `await Task.Delay(...)` in async code.

## Example

```csharp
// Violation
var result = client.GetAsync(url).Result;
```

```csharp
// Fixed
var result = await client.GetAsync(url);
```

## When to suppress

Suppress at a genuine sync/async boundary that can't be made async (e.g. a
legacy synchronous interface implementation, or a console app's
`Main` before top-level `await` was available) - and prefer
`.GetAwaiter().GetResult()` over `.Result`/`.Wait()` there, since it
doesn't wrap exceptions in an `AggregateException`.
